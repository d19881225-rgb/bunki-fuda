# 分岐札 外観改善計画書

作成日：2026年9月28日

対象：[公開サイト](https://d19881225-rgb.github.io/bunki-fuda/)

目的：初めて訪れた人が「どんな道具か」「どこから使うか」を理解し、疲れた日にも読み進めやすい外観に整える。

## 1. 最初にどうするべきか

**配色・文字・余白・カードの見せ方を先に揃える。機能や札を増やす前に、サイト全体の見た目の基準を決める。**

公開画面と実装を確認した。検索・選択・チェック・コピーの基本機能はある。今回はその機能を作り直さず、トップ・一覧・詳細の見え方を一つの基準で改善する。

採用する方向は「静かな、紙の道具箱」。温かい白、深い緑寄りの文字、淡い付箋色で、札を手に取るように使えるデザインにする。

## 2. 外観の判断と理由

| 現在の見え方 | 今回の変更 | 理由 |
| --- | --- | --- |
| 大きな黒い円・太い線・鮮やかな黄緑の分岐図 | 実在する札のプレビューを紙の束として表示 | 抽象的な図より、実際に読める内容と3手順を伝える |
| 見出しが大きく、文字間が詰まっている | 見出しの大きさ・行間を調整。本文は読みやすい端末内フォントを使う | 見出しだけが目立ち過ぎず、内容と操作へ視線が流れるようにする |
| 一覧の札が罫線で連続し、背景が同じ | 白い独立カードと間隔を設ける。PCは3列を基本にする | 一枚ごとの区切りが分かり、長いタイトルを読みやすくする |
| カテゴリは主に文字だけで区別 | 淡いカテゴリ色と文字ラベルを併用 | 目で探しやすくする。色だけに意味を任せない |
| 詳細ページのタイトルが最大86px | 読むための紙面として囲み、タイトルと3手順の大きさを調整 | 実行する手順と終了条件を主役にする |
| ボタン・検索欄・札の角や余白がばらばら | 角の丸み、入力欄、主操作と補助操作の形を統一 | どれが押せるか、何を先に押すかを示す |

これはデザイン上の編集判断であり、利用者調査やアクセス数から得た評価ではない。

## 3. 見た目の基準

| 要素 | 基準 |
| --- | --- |
| ページ背景 | 温かい白 `#f7f4ed` |
| 札の紙面 | 明るい白 `#fffdf8` |
| 本文 | 深い緑寄りの墨色 `#24302c` |
| 補助文字 | `#58615a`。薄過ぎる文字を避ける |
| 強調 | 淡い黄緑 `#e8edc5`。終了条件や選択中の状態に使う |
| 小さな差し色 | 落ち着いた赤茶 `#9b3f2b` |
| 書体 | 端末内の日本語フォント。外部フォントの通信・課金を追加しない |
| カード | 基本16pxの角丸。薄い境界線、控えめな影、十分な内側余白 |
| 文字の優先度 | 状況 → タイトル → 3手順への操作。詳細では手順と終了条件を重視 |
| 動き | 大きな動き・自動再生なし。押せる要素の色と境界で状態を示す |

## 4. 実施順序と完成の基準

| 優先 | 作業 | 完成の基準 |
| --- | --- | --- |
| 1 | 共通の配色・文字・余白・ヘッダーを整える | トップ、一覧、詳細、運営・プライバシーが同じ基準で表示される |
| 2 | トップの分岐図を実物の札プレビューへ置き換える | 洗い物の札の本文から3手順を表示し、詳細ページへ開ける。スマホでも隠さない |
| 3 | 一覧・検索・札選びを整える | 一覧はPC3列、タブレット2列、スマホ1列。カテゴリは色と文字で区別。1件・2件の検索結果も不自然に細くならない |
| 4 | 詳細・手順チェック・コピー・FAQを整える | 手順と終了条件が読みやすく、コピー等の主操作と補助操作が区別できる |
| 5 | 共有画像も新しい外観へ揃える | 1200×630の共有画像が新配色と紙の札を使い、タイトル・説明・公開URLを維持する |
| 6 | 動作・画面・公開を確認する | 自動テスト、ビルド、ESLintが通る。320px・390px・タブレット・PCで崩れを確認し、GitHub Pagesの公開成功と画面更新を確認する |

## 5. 変えないこと

- 既存20枚の内容、URL、検索語・かな検索、0件からの復帰、状況選択、手順チェック、コピー機能を保つ。
- GitHub Pagesでの一般公開を継続する。公開先を別サービスへ移さない。
- 新しい課金、会員登録、広告、外部AI、問い合わせ対応、入力保存は追加しない。
- 架空のレビュー、人気順位、効果の保証、収益の実績は掲載しない。
- 画像はコードで作る紙面・図形を使用する。購入素材や写真でページを重くしない。

## 6. 確認方法

1. 実装前に計画書と改善前の画面を記録する。
2. 主要な文字・背景の組み合わせのコントラストを自動確認する。通常の文字は4.5:1以上を基準とする。
3. 全23ページの静的出力、正規URL、20枚の内容と既存機能を自動テストする。
4. ブラウザでトップ・一覧・詳細を目視し、検索・状況選択・チェック・コピーを操作する。
5. 320px・390px・タブレット幅で横スクロール、見出しの切れ、ボタンの重なりを確認する。
6. 公開ビルドの成功後、公開ページで新しい外観と機能を確認し、本書に結果を追記する。

見た目の改善と、訪問者数・利用率・売上の増加は別の成果として扱う。今回は訪問者数や売上を計測しない。収益化は未設定のままとする。

## 7. 実施結果

実装前に本計画書を作成し、改善前の公開画面を記録した。計画の優先1〜5を実装した。

| 確認項目 | 結果 |
| --- | --- |
| 自動テスト | 23件すべて成功。20枚の内容・検索・選択・コピー・全23ページの出力を確認 |
| コード検査 | TypeScript、ESLint、差分の形式検査に成功 |
| 文字と背景 | 主要21組の配色が4.5:1以上。カテゴリ色上の本文・補助文字も確認 |
| PC | 一覧3列、1件の検索結果は広い一枚、2件は2列で表示 |
| タブレット | 768pxで一覧2列、横方向のはみ出しなし |
| スマホ | 320px・390pxでトップと詳細を確認。320pxで札選び、一覧、FAQ、運営・プライバシーも横方向のはみ出しなし |
| 既存機能 | かな検索、検索例、0件からカテゴリを広げて復帰、状況の選び直し、3手順チェック、コピー成功表示をブラウザで確認 |
| 共有画像 | 新配色の1200×630 PNGを生成し、文字の欠けがないことを目視確認 |
| 公開 | GitHub Pagesへの反映・公開画面の確認待ち |

ローカルでは既存の生成ファイル `.next/turbopack` に対するアクセス拒否でビルドが止まった。元データや公開用設定は変更せず、検証用フォルダーでwebpackによる静的ビルドを完了した。公開時は従来どおりGitHub ActionsのTurbopackビルドでも確認する。

参照：[W3C・文字と背景のコントラスト](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。本改善はサイト全体のWCAG適合認証を意味しない。
