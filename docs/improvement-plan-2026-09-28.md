# 分岐札 公開サイト改善計画書

作成日：2026年9月28日

対象：https://d19881225-rgb.github.io/bunki-fuda/

目的：必要な札を見つけ、短い手順を実行し、次回も使える無料ライブラリにする。

## 1. 最初に何をするべきか

**20枚ある札を、状況に合わせて探せるようにする。**

現状は「朝・仕事」の8枚が先に並び、残りは折りたたみの中にある。カテゴリ表示は押せず、検索もない。札を増やす前に、既にある20枚を利用者へ届ける導線を直す。

優先順位は、①見つける → ②実行する → ③また使う → ④公開品質を確認する、の順とする。

## 2. 現状と課題

2026年9月28日に公開画面と実装を確認した。アクセス数・利用率・収益の実測値は取得していない。

| 確認した事実 | 利用者への影響 | 改善方針 |
| --- | --- | --- |
| カテゴリ一覧が表示だけで、絞り込めない | 学び・家事・夜の札を探しにくい | 全20枚の一覧とカテゴリ絞り込みを設ける |
| 検索欄がない | 「洗い物」「資料」など自分の言葉で探せない | 状況・見出し・手順を対象に検索する |
| 2つの選択で札を返すが、具体的な状況を選び直せない | 同カテゴリの別の問題の札が出ることがある | 候補の状況を選べる補助操作を追加する |
| 詳細ページは読む・印刷・共有が中心 | 実行中の進み具合が分かりにくい | 3手順のチェックと終了条件を一緒に示す |
| スマホでヘッダーナビゲーションが非表示になる | 一覧や使い方へ移動しにくい | 小さな画面でも主要リンクを残す |
| 実際の札は2〜5分だが「3分で戻る」と表現している | 所要時間や効果について期待がずれる | 2〜5分の目安と、再開の入口を作る目的を明記する |
| 共有の中止・失敗が処理されていない | エラー時に次の操作が分からない | 中止処理、URLコピー、手動コピーを用意する |
| 詳細ページの共有情報がホームから継承される | 共有先で札ごとの内容が伝わりにくい | 各ページのタイトル・説明・正規URLを設定する |

## 3. 今回実施する改善

| 順番 | 内容 | 完了条件 |
| --- | --- | --- |
| 1・最優先 | 全20枚を表示し、カテゴリとキーワードで絞り込む | 家事の札4枚を表示できる。「洗い物」で該当札が見つかる。0件時は検索を解除できる |
| 2 | 2つの選択による札選びを維持し、具体的な状況も選べるようにする | 全5カテゴリ×2気力の組み合わせで候補がある。状況変更で対応する札に切り替わる |
| 3 | 手順チェック、やり直し、同じカテゴリの関連札を設ける | 3手順をチェックでき、完了表示が出る。やり直しで解除できる |
| 4 | 初回の使い方と短いFAQを追加する | 「探す→一つだけ実行→終了条件で止める」の流れが読める |
| 5 | スマホ、キーボード操作、印刷、共有を整える | 390pxと320px幅で横スクロールがない。主要リンクが見える。フォーカスが分かる |
| 6 | 共有情報・正規URL・404ページ・公開前確認を整える | 23ページが出力され、リンクとサイトマップが公開URLを使う。公開ワークフローが成功する |

実装中に確認した追加事項：依存パッケージ監査で修正版が必要なライブラリが見つかったため、Next.js 16.3.6、sharp 0.35.4へ更新し、関連パッケージも既存の指定範囲内で更新する。公開サイトは静的配信であり、Next.jsのサーバーを公開する構成ではない。

## 4. 運営条件と資産としての扱い

- 追加課金を伴うサービスを導入せず、既存のGitHub Pagesで公開する。
- 札、検索、選択、手順チェックはブラウザ内で動かす。外部AIへの問い合わせや個別対応は設けない。
- チェックや検索内容は保存しない。ページを離れると消えることを明記する。
- 既存20枚のURLを保つ。検索・共有・印刷から繰り返し使える情報資産として育てる。
- 今回の更新で売上が発生する仕組みは追加しない。現状の収益導線は未設定であり、公開完了と収益化完了は異なる。

## 5. 検証方法

1. ローカルの既存変更とGitHubの最新コミットを確認する。
2. 絞り込み・候補選択の自動確認と、静的出力の確認を行う。
3. ブラウザで検索、カテゴリ切替、0件からの復帰、候補選択、チェックの完了と解除を確認する。
4. スマホ幅とデスクトップ幅で表示を確認する。共有中止やコピー不可の処理も確認する。
5. ビルド・型確認・静的ページ確認を通過後、既存の公開リポジトリへ反映する。
6. GitHub Actionsの成功と公開画面の更新を確認し、実施結果を本書へ追記する。

## 6. 次の段階の判断基準

今回の成果は「目的の札を見つけて実行できること」で判断する。アクセス増や収益増の数値目標は、実測の基準値がないため設定しない。

次回の優先順位は、既存のアクセス情報が取得できる場合に、入口ページ・閲覧される札・検索流入を確認して決める。情報が取得できない場合は、代表的な利用場面の操作確認を続ける。

収益化は別の判断事項とする。候補は既存サイトへの広告だが、利用者の操作を妨げない配置、配信事業者の審査、データ取扱い、GitHub Pagesの利用条件をその時点で確認する必要がある。収益を保証するものではない。課金や対人業務を必要とする方式は、今回の条件には含めない。
